# Ambassador v1.0.0

**Released 15 November 2026**

The first public release of Ambassador: a production-shaped, MIT-licensed reference for creator and affiliate programs, with a product demo that runs in the browser.

## Highlights

- **Five Go services** — Users, Admin, Ambassador, Checkout, and an Email consumer — with Fiber handlers, GORM models, JWT authentication, and Kafka producers and consumers.
- **A real attribution path** — a referral code resolves to a creator and product, checkout writes the order and line items, and each line records a flat 10% ambassador / 90% merchant split.
- **Stripe Checkout sessions** in test mode, configured entirely through environment variables.
- **An event-driven backbone** — `product_*`, `link_created`, and `order_created` events flow through four Kafka topics, with consumer failures recorded in `kafka_errors`.
- **An interactive demo** — nine product screens, a 3D neural-network explainer with narration, a six-question quiz, an ROI calculator, and an interactive architecture map.
- **Deployment artifacts** — multi-stage non-root images, Compose stacks, Kubernetes manifests, OpenAPI contract, CodeQL, and CI.
- **Honest documentation** — the README and the demo both separate working code from simulated screens.

## What runs, and what is simulated

The Go APIs, MySQL persistence, JWT auth, Stripe Checkout session, Kafka events, and SMTP email consumer are real code. The nine product screens are a client-side simulation backed by `localStorage`; they do not call the APIs. Tiered commission rates and payout transfers appear only in the demo — the backend currently implements a flat 10% split and no Stripe Connect transfers.

## Security

- Hard-coded Kafka, Stripe, SMTP, and database credentials were removed from the current tree. **They existed in earlier commits, so rotate every credential that was ever committed.** See `SECURITY.md`.
- JWT signing now reads `JWT_SECRET`; without it the users service logs a warning and uses an insecure development default.
- Production images run as UID `65532`.
- Secrets and configuration are supplied through environment variables, Compose variables, Kubernetes ConfigMaps, and Kubernetes Secrets.

## Configuration changes

| Variable | Purpose | Default |
| --- | --- | --- |
| `JWT_SECRET` | Signs user JWTs | Insecure development fallback |
| `PORT` | HTTP port for each API process | `8000` |
| `REDIS_ADDR` | Redis address for the ambassador service | `redis:6379` |
| `KAFKA_GROUP_ID` | Consumer group for admin, ambassador, and checkout consumers | Service-specific |
| `DB_DATABASE` | Database for the current process | None; set per service |

Production images for Admin, Ambassador, and Checkout now include both `/app/service` and `/app/consumer`, matching the commands in the production Compose files.

## Known limitations

- No automated Go tests yet; CI runs build, vet, test, and format checks.
- `POST /api/checkout/orders/confirm` trusts the browser after the Stripe redirect. Signed webhook verification is not implemented.
- Commission rates are flat and the ledger does not model refunds, fees, tax, or adjustments.
- Stripe Connect payouts are simulated in the demo and not implemented in the backend.
- CORS allows credentialed requests without an origin allowlist, and there is no rate limiting.

These are documented in the README roadmap and are the right places to contribute.

## Verification

- `make build`, `make vet`, and `make test` pass for all five services.
- `go test ./...` currently reports no test files; this is expected for v1.0.0.
- `python3 scripts/check-links.py` validates the static demo.
- `docker build -f admin/prod.dockerfile` produces an image containing both `service` and `consumer` binaries.
- GitHub Actions runs the same build, vet, test, format, CodeQL, and link checks.
